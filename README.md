# TaskFlow Mini — Branching, CI and CD learning lab

No cloud, Docker, database, packages or app login required. Requires Python 3.10+, Git and a GitHub account for hosted workflows.

## 1. Run on Windows
Open this folder in VS Code / Codex terminal or PowerShell:

```powershell
python -m unittest discover -s tests -v
python -m app.server
```

Open http://localhost:8000 and add a task. Ctrl+C stops the server. If `python` is not recognized, install Python and enable PATH, or try `py` instead.

## 2. GitHub setup
Create an **empty** GitHub repository `taskflow-mini-lab` (do not initialize README). In this folder:

```powershell
git init -b main
git add .
git commit -m "chore: initial working application"
git remote add origin https://github.com/YOUR-USERNAME/taskflow-mini-lab.git
git push -u origin main
git switch -c develop
git push -u origin develop
```

GitHub authentication is required for pushing. Set default branch to `develop` in Settings > General > Default branch. The workflow file is `.github/workflows/ci.yml`.

## 3. Feature -> develop PR

```powershell
git switch develop
git switch -c feature/change-heading
```

Edit `app/index.html` heading from `TaskFlow Mini` to `TaskFlow Demo`. Then:

```powershell
git add .
git commit -m "feat: update taskflow heading"
git push -u origin feature/change-heading
```

GitHub > Pull requests > New pull request; base `develop`, compare `feature/change-heading`. Watch Actions > CI. Review and **Squash and merge**. `develop` push runs CI again and CD simulated `dev` artifact. GitHub > Actions > CD > latest run > Artifacts shows the simulated deployment. This is NOT an Azure deployment.

## 4. Release -> QA

First create a release from `main` and merge `develop` locally into it:

```powershell
git fetch origin
git switch main
git pull origin main
git switch -c release/1.0.0
git merge origin/develop --no-ff -m "merge develop into release 1.0.0"
git push -u origin release/1.0.0
```

The `release/*` push triggers simulated QA CD. Open PR with base `main`, compare `release/1.0.0`; wait for CI and QA sign-off before merge. For a closer manual QA approval simulation, configure a `qa` GitHub Environment with required reviewers if your repository plan supports that feature. If not, use a manual QA checklist and only merge when signed off.

## 5. UAT -> Prod

Merge release PR to `main` using **Create a merge commit** (not squash). The `main` push triggers UAT simulated CD. After UAT sign-off, go to Actions > CD - simulated environments > Run workflow, choose `main` and `prod`. It generates a simulated Prod artifact. For production gate, configure GitHub Environment `prod` with required reviewers if supported. Otherwise keep prod dispatch manual and do not confuse it with a technical enforced approval gate.

Tag the release:

```powershell
git switch main
git pull origin main
git tag -a v1.0.0 -m "Release 1.0.0"
git push origin v1.0.0
```

Sync release fixes back to develop via a separate PR (base `develop`, compare `release/1.0.0`), if there are any differences. This is a learning demo: no actual Azure deployments or infrastructure approval workflow.

## What to observe
- PR CI: `pull_request` runs tests before merge.
- Merge CI: `push` to target branch runs tests again.
- CD: branch push triggers simulated deployment artifact for Dev, QA or UAT.
- Production: explicit manual workflow dispatch; optional environment approval.
- Branch != environment. `develop` is code, `dev` is a deployment destination.
- Unit tests are real Python code in `tests/test_app.py`, not magically generated by YAML.

## Safety and realism
The proposed branching strategy is a draft. GitHub branch protection and environment approvals require separate repository settings and sometimes plan eligibility. The workflows are independent; the CD workflow runs its own tests before simulating deployment, rather than relying on the separate CI run. This lab is not a production-ready CI-to-CD artifact promotion chain. No credentials or Azure costs are required.
